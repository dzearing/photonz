Segmented control

· Component library Component library

One of a small set of exclusive options, with all of them visible at once. That last part is the entire reason it exists rather than being a .select: you can compare the options and hit one directly, without opening anything. It costs horizontal space to do that, which is why the rules below are mostly about when not to use it.

TrackA capsule of the same glass as every other control, 28px tall, with 2px of padding so the selected plate never touches the edge. SelectedA raised plate: its own fill, its own hairline, and --shadow-1. All three, because on a glass panel a fill alone is not enough contrast to find at a glance. SegmentA capsule inside a capsule, so round stays inside round. 11.5px, one line, never wrapped. One row, alwaysThe control is flex-wrap:nowrap and, when told to fill, a single-row grid. A wrapped segmented control reads as broken.

01

Anatomy

A capsule track holding capsule segments, and one of them raised. The selected plate carries fill, hairline and lift together — dropping any one of the three is how it ends up invisible on a glass panel, which is exactly what happened to the color picker's scope switch before this component existed.

Give the selected segment all three: fill, edge and lift. Mark selection with colour alone. On glass it disappears.

API node.fit = "cover". The options are enum("fit"), so the same list feeds the control, a menu, and an agent's completion.

02

Sizes & forms

Three heights, chosen by where it sits rather than how important it is: 24 in a dense panel row, 28 by default, 32 in a dialog or a toolbar. Two layout forms: natural widths when it sits in a row of other controls, equal columns when it owns the width.

Let it fill the column inside a panel, so a stack of rows aligns. Mix sizes in one panel. Pick the density once.

API the form is decided by location, not by an author: .pdock .seg and .cpick .seg take the equal-column grid automatically.

Six options in a 216px column. The second row has no left edge to align to and the two survivors stretch to fill it, so the wrap reads as damage rather than as a choice.

What happens now BooleanUnion

Six options never fit six visible segments in a dock, so it was the wrong control from the start. Above four options, or below about 44px a segment, it is a .select.

03

It never wraps

A wrapped segmented control is broken, not compact. The old rule tried to make the wrap look deliberate with equal auto-fit columns; the honest answer is that a control which cannot show its options is the wrong control. So the component is nowrap and single-row by construction, labels truncate before anything moves, and truncation is the signal to switch to a select.

Reserve it for 2 to 4 short labels with room to show them. Reach for a second row. Reach for a .select.

API both render enum("boolean"); only the presentation differs, so switching one for the other changes no behaviour and no command.

04

States

The selected segment does not have a hover state, because it is already the answer; hovering the others previews where the plate would move. A single disabled segment keeps its place in the row rather than disappearing, so the set does not resize under the pointer, and it explains itself in a tooltip.

Keep an unavailable option visible and say why in its tooltip. Remove a segment when it is unavailable. The row jumps.

API enum("fit") returns each option with its own enabled and disabledReason, so the control never decides this on its own.

Fit Scale A panel row

The most common home. Small size, right column, and the options are two or three short words.

A popover

Equal columns, filling the width. The color picker's scope switch: three answers to one question, all worth seeing.

A toolbar

Large size, for a switch that changes what the whole surface is showing. Rare, and never more than three.

05

Where it lives

Three homes, and the size follows the home. What all three have in common: the options are peers. A segmented control implies the choices are the same kind of thing at the same level, which is why it is wrong for a list that mixes a default with three exceptions.

Use it when the options are genuinely parallel. Use it as a two-state toggle. That is a .switch.

API selection writes straight through: view.workspace = "video".

This component had no owner before this page: it was styled in five different files at once, plus two bespoke copies inside the color picker, so the same control came out at two heights on one popover with a selected segment you could barely see. Everything about .seg is now in segmented.css and nowhere else. Compact windows: it takes the equal-column form and labels truncate; it never gains a row, and if truncation bites, the panel should have used a select.

The idea

A segmented control spends width to save a click. That trade is good when there are three short options and bad when there are six, so most of the spec is a boundary rather than a style.

A direction

Because a segmented control and a select render the same enum, a panel could pick between them from the measured width at build time. Authors would choose the property, not the widget, and no panel could ever be wrong about it.

Open question

Truncation is the signal that the control is wrong for its space, but nobody sees it until the window is narrow. Do we fail the build when a segment's label cannot fit its minimum, or accept the ellipsis and rely on review?
