Segmented control

· Component library Component library

One of a small set of exclusive options, with all of them visible at once. That last part is the entire reason it exists rather than being a .select: you can compare the options and hit one directly, without opening anything. It costs horizontal space to do that, which is why the rules below are mostly about when not to use it.

TrackA capsule of the same glass as every other control, 28px tall, with 2px of padding so the selected plate never touches the edge. SelectedA raised plate: its own fill, its own hairline, and --shadow-1. All three, because on a glass panel a fill alone is not enough contrast to find at a glance. SegmentA capsule inside a capsule, so round stays inside round. 11.5px, one line, never wrapped. One row, alwaysThe control is flex-wrap:nowrap and, when told to fill, a single-row grid. A wrapped segmented control reads as broken.

01

Anatomy

A capsule track holding capsule segments, and one of them raised. The selected plate carries fill, hairline and lift together — dropping any one of the three is how it ends up invisible on a glass panel, which is exactly what happened to the color picker's scope switch before this component existed.

Give the selected segment all three: fill, edge and lift. Mark selection with colour alone. On glass it disappears.

API node.fit = "cover". The options are enum("fit"), so the same list feeds the control, a menu, and an agent's completion.

02

Sizes & forms

Three heights, chosen by where it sits rather than how important it is: 24 dense, 28 default, 32 in a toolbar. Height is the only thing the size class changes — width is never set by the size, it comes from the labels, which is why two 28px controls next to each other are routinely different widths. That is the form, not a mistake: natural widths in a row of other controls, equal columns when it owns the width.

Let it fill the column inside a panel, so a stack of rows aligns. Mix sizes in one panel. Pick the density once.

Measured across the mock set: every one of the 51 controls in a real panel, dock or popover is 28px. Not one uses .sm; the only 24s and 32s live on specimen pages like this one. So 28 is not the default in theory, it is the only size the product actually uses — treat 24 and 32 as exceptions that need a reason.

03

It never wraps. It becomes a menu.

A wrapped segmented control is broken, not compact — so the component is nowrap and single-row by construction. But "then use a .select" was advice to whoever wrote the page, and a page cannot know how wide it will be. So the honest failure shipped instead: a four-option control at 120px truncated every label to 27px and read U… S… I… E…. The control now does it itself, and the trigger is measured rather than guessed.

Let it collapse. The menu still shows every option. Ship six segments and hope the dock is wide. It never is.

API the collapse is presentation only — same enum("boolean"), same .on class, same change event, so a page that already handles the control keeps working when it turns into a menu. .seg.no-collapse opts out; icon-only controls never collapse.

04

States & keyboard

The selected segment does not have a hover state, because it is already the answer; hovering the others previews where the plate would move. A single disabled segment keeps its place in the row rather than disappearing, so the set does not resize under the pointer, and it explains itself in a tooltip.

Keep an unavailable option visible and say why in its tooltip. Remove a segment when it is unavailable. The row jumps.

One tab stop for the whole control, then arrows move inside it, stepping over disabled segments. Arrowing does not wrap: off the last segment you stay on the last segment. You can see both ends of a segmented control, so they are real ends — jumping the plate from one side of the track to the other reads as the value having been reset rather than nudged. A menu wraps because you cannot see where its list stops; this can, so it stops.

API enum("fit") returns each option with its own enabled and disabledReason, so the control never decides this on its own.

What it used to do cross-fade

Selection lived on each button, so one plate faded out while another faded in. For about 60ms in the middle both segments are half-lit and neither reads as selected — the control blinks instead of answering.

What it does now reposition

One plate travels between slots. There is never a frame without exactly one selected segment, and the movement itself shows you which way the value went.

05

Changing the value

The plate moves, it does not blink. A segmented control changing value is the Move case in motion — reposition · spring · 240ms — because the selection is one object going somewhere, not two objects swapping opacity. It is also what the native macOS control does.

Animate position, so one plate is visible in every frame. Cross-fade two plates. Mid-transition nothing looks selected.

API segmented.js owns this. The plate follows the .on class with a MutationObserver, so it stays correct even when a page moves the selection itself. Listen with seg.addEventListener('change', e => e.detail.value). Under prefers-reduced-motion the plate still moves, it just arrives instantly.

Fit Scale A panel row

The most common home. Small size, right column, and the options are two or three short words.

A popover

Equal columns, filling the width. The color picker's scope switch: three answers to one question, all worth seeing.

A toolbar

Large size, for a switch that changes what the whole surface is showing. Rare, and never more than three.

06

Where it lives

Three homes, and the size follows the home. What all three have in common: the options are peers. A segmented control implies the choices are the same kind of thing at the same level, which is why it is wrong for a list that mixes a default with three exceptions.

Use it when the options are genuinely parallel. Use it as a two-state toggle. That is a .switch.

API selection writes straight through: view.workspace = "video".

This component had no owner before this page: it was styled in five different files at once, plus two bespoke copies inside the color picker, so the same control came out at two heights on one popover with a selected segment you could barely see. Everything about .seg is now in segmented.css and nowhere else. Compact windows: it takes the equal-column form and labels truncate; it never gains a row, and if truncation bites, the panel should have used a select.

The idea

A segmented control spends width to save a click. That trade is good when there are three short options and bad when there are six, so most of the spec is a boundary rather than a style.

Now settled

Because a segmented control and a select render the same enum, the control picks between them itself — from its own measured width, at runtime rather than build time. Authors choose the property, not the widget, and no panel can be wrong about it, including panels that get resized after they are written.

Open question

The threshold is one ellipsis of overflow, because the glyph costs about two characters and clipping less than that loses more than it saves. That is defensible but it is still a line: across the mock set it collapses exactly one control today, a six-option paint switch. Should a control that only just fits also collapse, on the grounds that it will not fit in a narrower window either?
