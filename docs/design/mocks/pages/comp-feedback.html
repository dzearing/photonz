01

Progress

Pick by what you know: the fraction, that it started, or a level. Never show an indeterminate bar for something measurable, and never a determinate one parked at 90% because you guessed. Anything running longer than about two seconds gets a label saying what it is doing.

Say what is happening, not just that something is. Block the canvas while work runs. Progress belongs beside the thing.

API a long command returns a task: task.progress (0..1 or null) and task.label. The component picks its own shape from whether progress is null.

02

Toasts

The workhorse. A toast reports; it never asks. It carries what happened, a thumbnail when there is one, and the one action that matters — usually Undo, which is what lets the app act first and confirm never. They stack from the bottom of the canvas, newest nearest, and a toast holding a running task stays until the task ends.

Put Undo in the toast. It replaces a confirmation dialog. Ask a question in a toast. It will time out and answer itself.

API every command that mutates returns an undo token, so the toast is generated rather than authored: run("image.removeBg") → toast with Undo.

A state with no number. The pulsing one means it is happening right now: recording, syncing, an agent working. The grey one is the macOS unsaved-changes mark.

03

The small marks

Three read-only marks that annotate something else. They are one file in the library because they were the three most-copied snippets in the app, each landing at a different size and weight every time. None of them is interactive, and that has to stay legible.

Use a filled badge. A 10% tint disappears on a glass panel at 16px. Give a badge a hover state. Then it is a chip, and people will click it.

API a badge is a view over a count or an enum; a dot over a boolean or a phase; a cap over command.shortcut.

04

Empty & error

Three different states people habitually collapse into one grey message. Nothing yet, nothing matching and something broke have three different ways out, so they get three different messages and three different buttons.

End every one of them with the action that resolves it. Show "No results" for an empty list that was never filtered.

API a list view takes empty, emptyFiltered and error separately, so the three cannot collapse into one by accident.

Five of six rows never interrupt. That ratio is the point: because every mutating command returns an undo token, the app can act first and report second, and the confirmation dialog stops being the default answer to "are they sure?". Reduced motion stills the indeterminate sweep and slows the spinner rather than removing it, since a frozen spinner reads as a hang.

The idea

Report, do not ask. Undo in a toast replaces almost every confirmation dialog an editor would otherwise grow, and it is faster for the person even when they did mean to do it.

A direction

Toasts already know which command produced them. A stack of them is a readable history, so the toast area could scroll back into the history overlay rather than being a separate surface.

Open question

Undo tokens have to survive long enough to be useful and not so long that memory suffers on a 12-megapixel document. Do we keep them by count, by bytes, or drop the pixel-heavy ones first and downgrade those toasts to plain reports?
