Component library

· the spec for what we standardize on Design system

Every control in Photonz comes from this library. It is a native macOS kit, not a web kit: capsule Liquid Glass surfaces, a luminous top edge, depth from the elevation ladder, and one 4pt size scale. Where the platform has an answer we take it. Where it does not, or where a photo editor needs something denser than a settings pane, we extend the language rather than borrow from the web. The pages in this section are the spec: anatomy, variants, states, rules, and the command each control maps to.

01

Five rules, no exceptions

One size scale (24 / 32 / 40, off the 4pt tokens). One state quartet on everything interactive: hover, pressed, focus ring, disabled. One elevation ladder, so no component writes its own shadow. One icon set, drawn to a single 24 grid. One accent, recoloured per role rather than per component.

Compose an existing component and scope your refinement. Ship an inert control. If it can be clicked it shows all four states.

API every control is a view over one command: run("file.export"). The look is the library's job, the behaviour is the command's.

Opacity62% The capsule thumb

The platform shape at inspector density: a horizontal pill on a thick groove. Wide enough to grab, and the round ends keep the fill visible right up to the value it is setting.

W The scrub label

Drag the label sideways to change the number. Every value in the app carries this, so you rarely have to aim at a slider at all.

Split at playhead ⌘⇧E The inverted label

Tooltips are the one surface that is opaque rather than glass: a 10px label over a busy canvas needs contrast more than it needs vibrancy.

02

Where we extend the language

Liquid Glass was designed for apps with a handful of controls on screen. A photo editor has two hundred. Our extensions all buy density and precision without breaking the material: same capsule geometry, same edges, same glow, applied to problems the platform kit does not have.

Extend by restating the existing geometry in a new place. Invent a second material because a control felt cramped.

API the extensions are visual only. layer.opacity = .62 is the same command whether you dragged the pill, the label, or typed it.

Filla vertical gradient, lighter at the top, so the surface catches light from above. --glass-thin / accent Edgea 1px hairline in --edge-lo, which is dark in light mode and darker still in dark mode. Glossan inset top highlight, --edge-hi. This one line is what makes a flat fill read as glass. Glowa filled control lifts in its own colour, not a neutral shadow. --glow, recoloured by --glow-c. Ringfocus is a 3px accent ring, never a shadow and never a border colour change alone. --ring. Contenticon and label on one line, icon from the shared set, shortcut in a .kbd cap.
03

Anatomy of a control

Six layers, in this order, on every control in the library. A component that skips the gloss looks flat next to its neighbours; one that hand-writes a shadow instead of taking a token drifts a little further every release. The layers are the contract.

Recolour a layer by setting its token on the element. Add a seventh layer. If it needs one it is a different component.

API node shared/check-elevation.mjs fails the build on a hand-written chrome shadow, so layer four cannot drift.

The pattern is consistent: containers map to the platform, value controls do not. Anything that edits a number precisely, in a dense panel, has to be built. That is where the work is, and it is also where the app either feels professional or does not.

The idea

A component library is a promise about density. Every control here is designed to survive at 24px in a 268px panel with forty siblings, because that is the real environment. A kit that only looks right in a settings sheet is not a kit for this app.

A direction

Each spec page ends with the command its control maps to. If we hold that line, the library doubles as the agent surface: anything a person can reach by clicking, a model can reach by name, with no second API to maintain.

Open question

The number field is the most valuable control we have to write from scratch and the most expensive. Do we build it once as a proper NSTextField subclass with scrub, arithmetic and unit parsing, or ship a simpler SwiftUI version first and accept that the inspector feels a grade less pro until it lands?
