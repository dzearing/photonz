Iconography

· one library, one grid, one hand Design system

Every glyph in Photonz comes from this one set. It is monochrome, it inherits currentColor, and it is drawn to a single grid so a toolbar, a layer row and a menu all read as the same piece of software. The library is the source of truth: if a glyph is missing, it gets drawn and added here, never substituted with an ascii symbol, an emoji, or a second icon style.

Nothing matches that. Try the concept rather than the glyph, or add the icon to shared/icons.mjs.

The idea

An icon set is a typeface, not a pile of pictures. One grid, one weight, one live area, so a row of icons sits as still as a row of text. Click any glyph to copy its markup.

Direction

The whole set is generated from shared/icons.mjs. Redrawing a glyph, restyling the weight, or adding a category is one edit plus one command, and the CSS, this page and the author docs all move together.

Open question

macOS ships optical sizes: small glyphs get a proportionally heavier stroke. We use one weight at every size. Worth cutting a second, heavier mask for 12 and 14, or is one weight the simpler promise?

01

One grid, four keylines

A 24 × 24 box with a 20 × 20 live area. Inside it, four keyline shapes: square, circle, landscape, portrait. A glyph is drawn to the keyline that matches its nature, never to the box.

The circle keyline is deliberately smaller than the square one. A circle at the same measure reads bigger than a square, and that single compensation is most of why the set sits still.

Fill the keyline your glyph belongs to.Let one glyph fill 24 units while its neighbour fills 14.

API the grid lives in shared/icons.mjs; run node shared/build-icons.mjs to publish.

02

One stroke, round ends

1.75 units on the 24 grid, round caps and joins, no fill unless the glyph is solid by nature: play, pause, keyframe, star, cursor, sparkle, the overflow dots.

Solid glyphs get drawn slightly smaller than line glyphs of the same job. Filled mass reads heavier, so a solid triangle at the full keyline would shout next to its neighbours.

Add a missing glyph in the same grammar.Mix a filled set and a line set in one toolbar.

API weight is the STROKE constant; changing it redraws all glyphs at once.

03

Five sizes, no others

Icons are sized by role, not by eye. 16 is the default and does most of the work; 12 and 14 exist for dense rows, 20 and 24 for surfaces where an icon is the subject rather than a label.

Anything smaller than 12 loses its interior detail and starts to read as a smudge. Anything larger than 24 shows that these are UI glyphs, not artwork, and should be a real illustration instead.

Pick the size class the surface calls for.Write width:15px because it looked better once.

API .ic.xs .ic.sm .ic .ic.lg .ic.xl; colour comes from currentColor.

04

Judged in place, not on a wall

A glyph is only correct once it holds up at 16px on glass, next to its real neighbours. The grid above is where it is drawn; this is where it is approved.

One concept gets exactly one glyph, app-wide. Add is always plus. A component is always component. The agent is always sparkle, on every surface, forever.

Test a new glyph in a tool bar and a layer row.Approve it from a 64px specimen and ship it at 16.

API <i class="ic ic-NAME"></i> works inside .tool, .btn, .lrow, .menuitem and badges.

The idea

Icons carry more of the app's character than any other single system, because they are on every surface at once. Getting them uniform is worth more than getting any one of them clever.

Direction

Two carve-outs stay text, not icons: keyboard symbols inside a shortcut hint, and typographic marks in running prose. Everything else that acts as an icon comes from this library.

Open question

Photoshop and Figma disagree on several of these glyphs. Where they conflict, do we follow the tool a user is most likely arriving from, or follow macOS and let both camps relearn one set?
