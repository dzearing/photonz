A component ships with real states, not just variants. Hover, focus, pressed, disabled and loading come free; custom states like Success or Destructive are named Paint plus Effect overrides attached to the component. You edit them where you edit everything else: select the component on the canvas and the Properties group in the one right dock shows its state list. That is the screen below. The idea

Every component ships with real states, not just variants. Built-in interaction states come free; custom states like Success or Destructive are named Paint plus Effect overrides swapped in by interaction, app logic, or the API.

A direction

A state is a partial override, so the same Success state can ride a Button, an Input, or a Switch. Wire one to a trigger and you have a working prototype: a tap runs set_state("loading"), and a successful save runs set_state("success"). Place it in the editor

Open question

Should a custom state be able to add or reorder layers in the tree, or only re-paint what is already there? Layer-adding states are powerful but harder to keep predictable across every instance.
