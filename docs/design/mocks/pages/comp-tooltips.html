Tooltips & inline help

· Component library Component library

A pro editor has a hundred icon-only controls, so the tooltip is not a nicety, it is how the toolbar is labelled. Ours is custom for three reasons the native one cannot cover: it carries the keyboard shortcut, it appears on keyboard focus as well as hover, and it can say why a control is disabled. Add data-tip to anything and you get all three.

Opaque --ink, not glass. A 10px label over a busy canvas needs contrast more than it needs vibrancy, and that is exactly when you are reading it.

Beak

Eased shoulders and a blunted tip, the same shape as the color picker's stop callout. One fill, no stroke, so there is no junction to leak.

01

Anatomy

Four parts, and only the shortcut is optional. The beak follows the same rule as every other corner in the app: eased shoulders, a blunted tip, no hard angles anywhere. It is drawn as one clipped path so the plate and the point are a single fill with nothing to seam.

Point the beak at the trigger, and move it when the tip flips. Sharpen the tip to a point. Nothing else in the app has one.

API the text is command.tooltip and the cap is command.shortcut. A page never types either one twice.

02

Placement

Above by default, because that is where your pointer is not. It flips when it would clip the window, and the beak follows: the plate can slide sideways to stay on screen while the beak stays pinned to the trigger's centre, which is the difference between a tooltip that points and one that floats near.

Let it flip. A clipped tooltip is worse than none. Recentre the beak with the plate. Then it points at nothing.

API data-tip-side="left" overrides the default when a control sits at the edge of a rail and above is always wrong.

03

The gap

The one number people get wrong, because the obvious way to write it is wrong. The gap belongs between the beak's TIP and the control, and the beak sticks out about 9px past the plate. Offset the plate by the gap alone and the point lands on the control, the tooltip reads as growing out of it, and the beak stops looking like it is pointing at anything.

Offset by gap + beak, and measure the gap from the tip. Offset the plate by the gap. The beak eats all of it.

API GAP · BEAK · BEAK_SIDE in tooltip.js. One place, so the four sides cannot drift apart.

To open 1s of a still pointer

The clock restarts on every mouse move, so it measures a pause, not time spent inside the control. Crossing a toolbar to reach the far end never pops anything, because you never stopped.

To swap 60ms, no animation

Once one is open the label swaps in place. You already asked for tooltips by resting once; re-earning it at every neighbour would make walking a toolbar feel broken.

To close 450ms of grace

Slipping off the glyph, or onto the 4px gap between two buttons, is travel rather than dismissal. Without the grace you had to hold dead still to finish reading a shortcut.

Sweep across these tools without stopping: nothing appears. Now stop on one and wait a beat. Once it is up, walk the row and the labels follow you.

04

Timing & motion

Rest, not dwell. A plain dwell timer cannot be tuned: raise it and deliberate hovers feel sluggish, lower it and every sweep flashes labels you did not ask for. Gating on stillness removes the trade, because a sweep is silent at any value — so the number only has to answer "how long is a pause that means I want help".

Opening, swapping and closing are three different events and take three different numbers. They are easy to collapse into one and it is always wrong: the same 60ms that makes a swap feel instant makes a close feel like the label was snatched away.

Keep the fade on exit even when the entrance was warm. Let a tooltip survive a brief trip off its control. Animate the swap. Sweeping a toolbar becomes a slideshow. Make the keyboard wait out the rest timer. There is no pointer to hold still.

API DELAY_IN 1000 (rest) · DELAY_FOCUS 120 · DELAY_SWAP 60 · DELAY_HIDE 450. Escape, a press or a scroll bypass all four and hide at once: those mean gone, not moving on. Reduced motion keeps the fade and drops the travel: the fade is what tells you a new label appeared, so removing it would remove information rather than decoration.

05

What it says

The test: would a person who already sees the control learn something? If not, the tooltip should not exist. A tooltip on a button that already reads "Export" is noise; a tooltip that says why Export is greyed out is the most useful thing on the screen.

Explain a disabled state. Always. Repeat a visible label word for word.

API command.enabled and command.disabledReason ship together; the tooltip shows the reason automatically when the first is false.

Hover any tool, then press Tab to walk them with the keyboard. The disabled one still explains itself; the last one is forced below.

06

Behaviour

Timing is on the previous block; this is everything else. It shows on keyboard focus as well as hover, so tabbing a toolbar names every tool. It vanishes on press, because you have committed and the label is now in the way. It never survives a scroll or a drag: a label that outlives the thing it labels is pointing at whatever moved into that spot.

Show on keyboard focus too. Tab is how a lot of people explore. Keep it up during a drag. It follows the pointer into the canvas.

API data-tip="Label|⌘K" on any element. A stray title is upgraded to one automatically, so no control can accidentally end up with a label that keyboard users never see.

07

Three ways to explain something

Pick by how long the explanation needs to live. A tooltip is a whisper you did not ask for and must not block anything. A callout is documentation you opened on purpose. Inline help is part of the layout because the setting is genuinely obscure and always will be.

Promote to inline help when people keep hovering the same control. Put a paragraph in a tooltip. If it needs a paragraph it is not a tooltip.

API all three read the same command.help string; the surface decides how much of it to show.

Compact windows change nothing: the tooltip is already the smallest surface in the system and it flips rather than shrinks. The idea

Tooltips are the app's keyboard-shortcut teacher. Every one carries its command's shortcut, so the way you discover the fast path is by using the slow one, and nobody has to read a shortcuts sheet.

A direction

The tooltip could show a tiny live preview for tools with a visual result: the brush's actual tip at its actual size, the transition's first frames. It is the same surface, with the label demoted to a caption.

Open question

Disabled controls do not receive mouse events on macOS, so showing a reason means keeping the control enabled and failing loudly, or overlaying a transparent hit target. Both have costs. Which one do we take?
