In the API

Everything above is one call each · address any level by its path

A nested component is a layer tree of instances. You reach into any depth by path. Overrides are stored on the instance you address; the mains they point at never change, so one edit to a main still fans out everywhere it is used.

// override a value that lives inside a nested instance appBar.override("toolbar.title", "Files") // swap a slot's variant, still linked to the same main appBar.swap("toolbar.action", "IconButton/Ghost") // edit the deepest main once · all 3 linked instances follow IconButton.set({ radius: 12, tint: "comp" }) // clear a level's overrides · re-link it to the main appBar.resetOverrides("toolbar.title")
The idea

Composition goes all the way down. An IconButton is used inside a Toolbar, which is used inside an AppBar. Each level can override a value that rides inside it, yet the deeper mains stay linked, so one edit to a main updates every instance that did not opt out.

A direction

Overrides are addressed by path, the same way a command is · appBar.override("toolbar.title","Files"). Because every override is one call, an agent can retheme a whole nested tree, and a token or style change can flow through every level at once.

Open question

When you edit a linked instance in place, should we auto-detach just that property into an override, or ask first? And should an override be pushable back up to become the new main default, the way push to main hints at here?
