Tool bar & command surface

· Design language Design language

The shipping app is canvas-first, so it has no options bar and no wall of chrome across the top. Tools live in a floating bottom tool bar that hovers over the canvas: the tool strip, the foreground and background colour pair, and zoom. Commands live in the native macOS menu bar, and the mock stands in for it with a compact command surface plus the ⌘K palette. Two bars, both small, both fixed in place, so muscle memory holds while scope grows. Every button is a named command, so an agent presses the exact same one you do.

Left to right: the command surface (a menu button that opens a grouped popover), the ⌘K palette, the History entry that opens the slide-down overlay, a spacer, and the active design system. That is the whole row. It never grows a tool.

Why there is no fake menu bar. In the shipping app the real command surface is the native macOS menu bar (File, Edit, Select, Layer, Type, Effect, View, Window, Help), and it is the plainest proof that everything the UI does is one API call. The mock lives inside an iframe, so drawing a full horizontal menu bar would read as fake chrome. Instead the mock shows the compact command surface plus ⌘K and says out loud that the menu bar is the real one. There are four equal ways to reach any command: the tool strip, a right-click, the command surface, and ⌘K. An agent uses the same calls.

03

Variants · the canonical tool inventories

Decision D4 · shared tools keep glyph and slot

The strip order is fixed: Select → create and edit cluster → measure and crop → Hand → Zoom. The inventory belongs to the document kind, chosen once at New: an image document carries the image tools, a UI document the frame and component tools, a timed document the blade. Shared tools keep the same glyph and the same relative slot in every kind, so moving between documents never makes you hunt. A kind that lacks a shared tool omits it; it never re-slots the ones it has. Tools marked .ovf fold into more when the window narrows.

Every tool is a real button, so hover, press, keyboard focus and disabled all come from the one control system. Only one tool in a strip is active at once, and active fills with the accent. There is no options bar. Tools are global and always in the same place; the options for the active tool are contextual, so they lead the Properties group in the dock, above whatever the selection contributes. That keeps a growing tool set from growing a new row of chrome every release, and it means the options are next to the rest of the settings you are about to change. A tool with one or two options may instead use a popover on the tool itself.

08

Rules

Do / Don't
Keep the order Select → create → measure → Hand → Zoom, in every document kind. Re-slot or re-glyph a shared tool because a page needed room. Split clusters with a thin separator, never a box. Add a permanent options-bar row. Tool options lead the Properties group. Mark low-frequency tools .ovf so they fold into more when narrow. Drop a tool at a small width, or move it to a different surface. Print each tool's single-key shortcut in its tooltip. Two active tools in one strip at the same time. Keep the command row to commands: menu, ⌘K, History, the active system. Draw a fake macOS menu bar. The real one is native and always there.
09

In the API

Every button is one named command
run("tool.crop")Picks a tool. The strip highlights it, the cursor changes, and the Tool options section swaps.
tool.activeReads back the current tool, so an agent can restore it after doing its own work.
tool.optionsThe active tool's option set. The same values the Properties group shows.
document.kindReads the document's kind, fixed at New. The strip and panels follow it; there is no live mode to set.
view.zoom = 1.0The zoom control. "fit" and "100%" are named values.
palette.open()Raises ⌘K, the fourth equal way to reach any of the above.

Four equal paths to one call: the tool strip, a right-click, the command surface, and ⌘K. That is why an agent can drive the app without a special mode. See it whole in App shell.

The idea

One small floating bar holds the tools, the colour pair, and zoom, and it floats so it costs the document nothing. Learn it once on a screenshot and it reads the same on a component or a video clip, because the same command drives every button.

A direction

The strip could be user-pinnable: promote the two tools you reach for most in a given document kind out of more and into the strip, remembered per document, without ever changing the order of the shared tools around them.

Open question

When several objects of different types are selected, the tool options are unambiguous but the selection properties are not. Does Properties show the intersection, the union with disabled extras, or a plain "mixed selection" summary?
