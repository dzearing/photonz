The window frame

· Design language Design language

The frame is the glass boundary around one document: traffic lights, the document identity, a quiet status readout, and Ask. Photonz is one document per window, so the window is the document. The title bar is the only chrome that is always on screen, which is exactly why it carries nothing but the document. Tools live in the floating tool bar, panels live in the dock, and commands live in the menu bar and ⌘K. On this page the complete windows are real app screens; the cut strips are labeled title-bar specimens.

The one rule that keeps every window honest: the title bar carries document identity only. A lesson title, a feature name, or an explanatory phrase ("Vector pen · resolution-independent shape") is teaching copy, and teaching copy belongs in the page heading or a caption, outside the window. If a window wears traffic lights it is claiming to be the app, so it has to be the whole app: title bar, command surface, canvas with its floating tool bar, and the dock. Anything less should be a labeled specimen instead.

05

Rules

Do / Don't
Carry document identity and nothing else: name, edited dot, context. Put a lesson title or a feature name in the title bar. Keep Ask hard right, alone. It is the one affordance the title bar carries. Put Share, Export, Done, a lens switcher, zoom, a tool, or a panel toggle up here. Document actions belong to the native menu bar; the rest live in the tool bar and on the canvas. Show the edited dot the instant a change lands, and clear it on save. Close destructively without a save prompt. Fold actions into one overflow menu before the name truncates. Grow a second row of buttons, or stack two documents in one window. Dim the whole frame together when the window is not key. Wear traffic lights on anything that is not the complete app.
06

In the API

One command per part
window.open("settings-capture")Opens the document in its own frame. One document per window, always.
document.name = "launch-hero"Renames the file; the identity in the title bar reflects it live.
document.editedRead-only. true drives the edited dot; document.save() clears it.
workspace.set("video")The lens switcher. Same document, different tool strip and panels, timeline only when the document has time.
run("export")Every title-bar action is a named command, and the overflow order is declared, not guessed.

Every part of the frame an agent might touch is one call, so the surface a person drives is the surface the agent drives. See the whole shell in App shell or a working document in the editor.

07

Responsive

Two breakpoints, one markup

The window is the container-query root (.win.cq), so the frame answers to the window width, not the screen. At 880px the dock rails and becomes an overlay, the tool bar's overflow tools fold into more, and the title bar drops the document size and then the status readout. At 620px the rail drops its labels, the zoom slider drops out, and Ask drops its ⌘K hint, then its label. Verify by narrowing the window, never by drawing a separate small mock.

The idea

The frame is the one piece of chrome always on screen, so it stays calm and literal: which document, is it saved, which lens, what can I do with the whole file. Everything else has a home somewhere closer to the work.

A direction

The edited dot could double as the save affordance: click to save, hover for a one-line summary of what changed since the last save, so the state indicator is also the control.

Open question

Strict one document per window is clean, but a redlining session opens a dozen crops at once. Do we add a lightweight window switcher in the frame, or lean on macOS tabs and Stage Manager and keep the bar empty?
