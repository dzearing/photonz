Buttons & actions

· Component library Component library

There is one button system, .btn, and four other action controls that exist because a toolbar, a tag and a segment are not buttons even though they can all be pressed. The rule that keeps this from sprawling: if it performs an action and lives in prose, a dialog, a panel body or an empty state, it is a .btn. Everything else has an established slot, and you reach for it only in that slot.

01

Anatomy

Icon, label and shortcut sit on one line that never wraps. A button is a capsule because a capsule says "press me" at any size; the fill is a vertical gradient so it catches light from above, and one inset highlight along the top edge is what makes it read as glass instead of paint.

Lead with the icon, then the label, then the shortcut. Wrap a label to two lines. Shorten the label instead.

API a button is a view over a command: run("file.export"). Its label, icon, shortcut and enabled state all come from the command, so a menu item and a button never disagree.

Primary .primary

The one thing this surface is for. Never two on screen at once. Glossy accent glass, lifts in its own colour.

Secondary .secondary

The default. Neutral glass. Everything that is a real action but not the action.

Ghost .ghost

Transparent until hovered. For dismissal, and for dense rows where a bordered button would be visual noise.

Danger .danger

Destructive and hard to undo. Recolours the glow and the focus ring, so even keyboard-only use reads red.

Hero .hero

The agent's own surface, and the only control that does not wear the app's accent. Hover opens the spectrum rather than tinting it.

02

Variants

Five. Four are graded by consequence, not emphasis — ask what happens if the user presses it by accident: nothing → ghost; something ordinary → secondary; the thing they came for → primary; something they will regret → danger. Hero is not on that scale. It marks the one control per surface that is not a command at all, but the way into the agent, so it is the only one that answers "what kind of thing is this" rather than "how much will it cost me".

Exactly one primary per surface, on the right of a footer. Use danger for "Remove from list". Danger means data is gone. Reach for hero to make an ordinary button louder. A second hero makes both ordinary.

API destructiveness is a property of the command (command.destructive), not a styling choice, so the danger look cannot be forgotten on one of the three places the command appears.

03

Sizes & shapes

Three heights off the 4pt scale, and the size is chosen by where it sits, not how important it is: 24 in a dense panel row, 32 everywhere by default, 40 in a dialog footer or an empty state. Importance is the variant's job.

Keep one size per row. Mixed heights read as a mistake. Shrink a button below 24px to make it fit. Cut the label.

API a split button remembers per document: command.lastVariant("file.export") is what the left half runs.

04

States

Hover brightens the fill and widens the glow. Pressed insets rather than darkens, so the control feels physical. Focus is a ring, never a border change. Working swaps the icon for a spinner and keeps the button the same width so the row does not jump.

Disable a button only when you can say why in a tooltip. Grey out with no explanation. A disabled control with no reason is a dead end.

API command.enabled and command.disabledReason come as a pair. The reason is what the tooltip shows.

.tool toolbar icon

A mode, not an action. It stays on until you pick another. Only inside a toolbar or tool strip.

3 layersAsk .pill status capsule

RoundedTitle/LCard .chip tag / filter

Names a thing (a style, a component, a filter). Pressing selects or applies it, never "does" something.

.seg segmented

One of 2 to 4 exclusive options, all visible. Above 4, or where space is tight, use a .select.

05

The four that are not buttons

They are pressable, so they take the same hover, press, focus and disabled response as .btn and the same capsule radii. What differs is the promise: a tool sets a mode, a pill reports state, a chip names a thing, a segment picks one of a set. None of them performs a one-shot action.

Use the established control for its established slot. Put a .chip in a dialog footer because it is smaller.

API a tool is run("tool.brush") and stays current; a button's command runs and returns. The difference is in the command, not the pixels.

06

Grouping & order

macOS order, always: the confirming action is furthest right, cancel to its left, and a third choice like "Don't Save" is pushed to the far left with real space between. Related icon actions sit in a tight run with no gap; unrelated ones get a separator.

Let the layout do the ordering so a page cannot get it wrong. Put the primary on the left because it reads first in English.

API .dlg-f lays out the footer; a third option takes .away and the rule follows automatically. See Menus & dialogs.

Every one of these is the same command surfaced differently. That is the whole reason the library is worth holding to: a command knows its label, icon, shortcut, enabled state and destructiveness, so the button in the toolbar, the item in the menu and the line an agent issues can never drift apart. Compact windows drop labels before they drop buttons: a .btn becomes a .btn.icon with the label moved into its tooltip, and only then does the overflow menu take the rest.

The idea

Four variants chosen by consequence and three sizes chosen by location. Two independent axes, neither of them "how much do I want this noticed", which is the decision that makes button systems rot. Hero sits outside both, and stays legible precisely because it is spent on one thing.

A direction

The split button remembers per document. We could take that further and let the whole toolbar reorder itself around what you actually use in a given document type, with a "reset to standard" always one click away.

Open question

SwiftUI's .glassEffect gives us the material for free but not the four variants, and overriding it costs us the platform's future refinements. Do we accept the divergence for danger and ghost, or restyle only within what the modifier exposes?
