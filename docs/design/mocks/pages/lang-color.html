Color & interaction states

· Design language Design language

Color in Photonz is role-based, never decorative. A token names a job (text, surface, line, accent, component, semantic), and the theme resolves it to a real value for light or dark. You style with the role, so the same UI reads correctly in both themes and an agent that sets a color sets a role, not a hex. Interaction states layer on top: every control moves through rest, hover, focus, pressed, disabled, and selected using the same small set of tokens.

The role set

Six families. Text, surface, and line build the chrome; accent and component mark what you can act on and what is reusable; semantic is held in reserve. Scenario accents only pip the workspace so you always know if you are in an image, a video, or automation.

API theme.roles lists the set; a component references roles, so retheming is one token swap.

03

Interaction states

One ladder for every control: rest, hover, focus, pressed, disabled, selected. Hover and press only shift brightness of the rest color, focus is always a 2px accent ring, and selected uses the soft wash so it never competes with focus.

Keep the focus ring visible for keyboard users.Skip hover feedback on a clickable thing.

Light / dark in context

The two panels are the same markup. Ink stays legible, accent stays the action color, purple stays "component", crit stays the warning. Only the resolved values change, and the theme keeps contrast in range on both.

Test a screen in both themes before shipping it.Pin one theme's hex and hope the other survives.

API theme = "dark" re-resolves every role. Auto follows the system appearance.

Accent is not a status. Purple is not a highlight. Red is a real problem, not emphasis. When in doubt, use text and line roles and let content carry the color.

05

Rules

Let accent mean "actionable", nothing else. Keep contrast legible: ink on panel, never faint on faint. Reserve green / amber / red for good / warn / crit. Hardcode a hex for chrome; use the role token. Treat accent as semantic, or red as emphasis.

API a lint flags any raw hex in chrome and any semantic color used for decoration.

06

In the API

Color is addressable the same way the UI touches it. Set a role, not a value; ask the theme to resolve it; apply a state as a modifier. Everything the color picker does is one call, so the agent themes exactly what you do.

07

Responsive

Roles never change with width, only their presentation. Swatch cards shrink to chips, names move into tooltips, and the state ladder keeps its full contrast so a small window is still readable.

Drop the label before you dim the swatch.Weaken a focus ring to save space.

API presentation is a view concern; color() and state() return the same values at any size.

The idea

Color is a set of roles, not a palette of hexes. Name the job once and the theme does the rest, so light and dark, the UI and the agent, all stay in agreement.

A direction

Roles could extend into Styles: a paint style like "Brand" is just a named bundle of roles and stops, so retheming a whole document becomes one swap and every component instance updates with it.

Open question

How far do we let a document override the theme? A per-document accent is expressive, but the moment a screen ships two accents the "you can act here" signal starts to blur. One override, or none?
