Does the app need project types?

· study · asked, drawn, answered

A document today is a canvas with a size. Nothing anywhere asks what you are making, so a person drawing a 24 point glyph is offered the measure tool, the highlighter and the zoom callout, and one day would be offered a video timeline too. The proposal is that the app should ask at the front door and then show one set of things for an icon and another for a recording. The answer this study reaches is no to the gate and yes to the front door. Asking what you are making is worth doing, because it can set up the canvas, the zoom, the grid and the export for you in one click. Using the answer to HIDE things afterwards is the part that does not pay, and it fails on a document the app already lets you make: a 24 point icon frame sitting beside a 1440 point screen, in one window, both of them real work. Everything below is shown rather than asserted, and the one fact the whole argument rests on is pinned by a test that runs in the suite.

1

Document, two kinds of work

An icon frame and a screen frame live in the same document today, and the app is already right about both at once. DocumentHasNoKindTests proves it: isIconFrame is true of the 24 and false of the 1440 in the same breath.

The proposal

Nothing on this sheet is objectionable, and most of it is a real improvement on what is there now. Today the same moment is a list of five screen sizes and a Custom row, which answers "how big" without ever answering "what for", so a person who wants to draw an icon has to already know that 24 by 24 is the answer and that they will want the zoom at 1600%. Picking Icon here could make the frame, set the zoom to something you can draw at, put the keylines up and default the export to SVG. The whole of the disagreement in this study is about what happens NEXT: whether that answer is remembered as a setup that already happened, or kept as a rule that keeps deciding what you are allowed to see.

Read the last row honestly, because it is the best case for the idea. Five slots off an icon's bar is not nothing, and seven off a recording's is a lot. The counts are also the most generous version: "rare" was counted as keep, so nobody can say the table stacked the deck. Two things take the shine off. The first is that Capture removes nothing at all, and capture and redline is the app's main real-world job, so for the primary user the entire feature is invisible. The second is the more serious one: the recording column is a column about a window that already exists. Video in Photonz today is a separate editor with its own state and its own window, so it is not showing icon tools now and does not need a project type to stop. The only column where hiding is both real and unsolved is Icon, and five buttons in a grouped strip is a small prize for a rule that has to be right about every document forever.

The usual answer to this is an escape hatch, and the escape hatch is where the idea eats itself. Put a "Show all tools" switch in and the bar becomes something a person toggles when they cannot find things, which is two states of the app to learn instead of one and a support answer instead of a feature. Leave it out and the app is lying about what it can do. Offer the tool anyway the moment it is needed and you have built the contextual answer in section 5 with an extra dialog in front of it.

The crux

One document, honestly two kinds of work, and the app is already right about both

Not a proposal: this document can be made in Photonz today. Pinned by Tests/PhotonzCoreTests/DocumentHasNoKindTests.swift.
notification-bell · 24 × 24 · icon frame
Settings · 1440 × 1024 · screen frame

This is the sentence a project type cannot say. The bell is the app's notification icon and the panel beside it is the screen the icon appears in; drawing them together is the point of having frames at all, and it is how anybody checks that a 24 point mark reads at the size it will really be seen at. The app is already right about both halves at the same moment: isIconFrame answers true of the 24 and false of the 1440, iconFrameID(containing:) returns the bell's frame for a stroke drawn on the bell and nothing for a caption drawn on the panel, and a fresh line starts at 2 points inside the icon and at the tool's own 4 on the screen. Three tests run that in the suite. Ask this document what kind it is and there is no answer, and the two escapes both cost more than they save: forbid the mixed document and you have removed the reason frames exist, or add a fifth kind called Mixed that hides nothing, which is the typeless app with a label on it.

The difference between these two windows is bigger than the difference between the two kinds in section 2, and nobody was asked a question to get it. It is also right more often, because it is re-answered every time the selection moves rather than once at the moment you knew least. The rule has three legs and two of them are running in the app already. The frame you are in: an icon frame puts the size row up and starts a line at whole pixels (IconPreviews, IconStrokeWeight), and a screen frame brings layout. What you have picked: the pane shows the sections that layer has, which is how it works today. What the document contains: something with a duration gets a transport, something with a repeating motion gets a cycle strip, which is what the animation study landed on. One leg is genuinely missing, and it is worth saying rather than hiding: a picture opened from a file becomes the canvas itself with no frame around it, so a capture has nothing for the context to hang off. That is the one real piece of work this answer creates, and it is a smaller piece than a project type.

Migration

Every document that already exists has no kind, and that is not a gap to fill

Every .photonz package on disk, every screenshot anybody has annotated, and every file the app has ever written.

Under the gate answer, old files force the feature to defeat itself. They carry no kind, so on open the app has three choices and none of them is good. It can ask, which is a dialog in front of a file somebody just double-clicked, to answer a question about a document they already know. It can guess from the contents, in which case the guess is doing the work and the question at the front door was never needed. Or it can give them a no-kind state that hides nothing — and then that state has to be a good place to work, because it is where every old file lives, which makes the four kinds a decoration on top of an app that has to be complete without them. The third option is the only humane one and it is also the admission.

Under the answer this study recommends, nothing happens to them at all. There is no kind to be missing. An old document opens and the pen is armed at 2 pixels inside its 24 point frame and at 4 on its screen frame, for exactly the same reason a new one is, because the rule reads the document rather than a label attached to it. A file made today keeps working in a build from a year ago, and a file made a year ago gets every improvement made since. That is worth more than it sounds: a kind stored in a file is a compatibility promise forever, and the kinds we would invent now are the kinds we understand now.

Cost

What it costs us to be wrong, in each direction

Both of these are real risks. They are not the same size, and the reason is that only one of them is quiet.

If we build none and that was wrong
What it feels like
The app looks broken rather than focused. A tool that is genuinely in the product is missing from the bar, and nothing on screen says why or offers it back. The person concludes the feature does not exist.
The app feels busy. Every surface carries every tool, the bar grows each time something ships, and a beginner drawing an icon has to ignore things rather than not see them.
How we find out
We mostly do not. Nobody files a report saying a tool they never knew about is hidden. It shows up as people using the app less for things it is good at.
Immediately and loudly. "There is too much in here" is the easiest complaint in the world to make, and this loop already turns one into a task the same day.
What it costs to undo
High. A kind is stored in the file, so it is a format, a migration and a promise to every document written while it existed. Removing it later means deciding what those documents become.
Low. Nothing is stored, so the fix is adding a rule about when something shows, and the rule can be tried behind a flag on one surface at a time.
The honest risk
We spend the icon epic building a gate, the primary user never sees it because Capture hides nothing, and we own it forever.
The bar and the pane keep growing and nobody stops them, which is a real thing that is already happening: the pane asks 1052 points of 968.
What limits it
An escape hatch, which as section 3 says is where the idea stops being a feature and becomes a setting.
The contextual rule in section 5, plus the front door in section 1 doing the setup. Both are on this page and neither stores a kind.

This is why the answer is not symmetrical. The no-kinds failure is loud, cheap and reversible, and we already have a working mechanism for hearing about it. The kinds failure is quiet, expensive and written into the file format. Given two risks of similar likelihood, take the one you will hear about.

Recommendation

Keep the front door. Do not build the gate.

Three slices, each judgeable on its own, none of which stores a kind in a document.
1

New asks what you are making, and sets it up

The sheet in section 1, with the gate taken out. Icon makes a 24 point frame at a zoom you can draw at with keylines up; Screen makes a 1440 frame with the layout grid; Capture takes a shot; Recording opens a file. It is a starting point, not a mode: nothing is hidden and the choice is never stored.

2

A picture you open arrives in a frame

The one hole in the contextual rule. Today a screenshot becomes the canvas itself, so there is no frame for capture context to follow. Give it one and measure, spec export and the annotation tools have somewhere to belong, and the same document can then hold a capture and a design side by side.

3

The pane earns its room by relevance, not by permission

The crowding is in the side pane, and it is measured. Sections appear because the frame, the selection or the document has something to say, and the ones that do not stay shut. That is the same saving a kind promised, taken per document region and without a question at the front door.

What this explicitly does not include. No kind is stored in a document, so no migration, no compatibility promise and nothing to be wrong about an old file. No tool is removed from the bar by declaration. And the one case that could still change the answer is named rather than buried: the day video moves into the layer document, one document could hold a fourteen second recording and a 24 point glyph at once, and the pane would have to carry a transport and an icon size row together. That is an argument for the context rule getting sharper, not for a kind, because a kind would have to call that document one thing and it is two. If it ever does become unbearable, the thing to reach for is a WORKSPACE, a saved arrangement of panels you switch between and can always switch back from, which is a view setting and not a property of the file. That is a different feature from the one being asked about here, and it can be added later without undoing anything on this page.
